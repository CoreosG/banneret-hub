# The fake relay

`packages/banneret-relay-fake` is a test double for the `/relay/v1` contract in this folder, plus a
conformance suite that runs against any relay. It is never a production relay: by default its state lives in memory,
enrolment has no sign-in page, and a test can approve or refuse any pairing. Release builds do not include it.

## Run it

```sh
node packages/banneret-relay-fake/src/bin.ts --port 0
```

It prints its origin, such as `http://127.0.0.1:41234`. The API is under `/relay/v1`. By default every
pairing is approved as soon as it starts, as the founder `ada-example`. The staff directory starts with `cy-example`, a limited staff member
who has never signed in and has no machines or sessions. Options:

- `--config <path>`: read health sources, dashboard links, critical recipients, board clocks and the optional alarm database path from a private JSON file.
- `--manual-approval`: pairings wait until a test confirms them through the control surface below.
- `--network-identity-header <name>`: turns on the optional network identity check, reading the caller's
  identity from that request header.
- `--public-origin <url>`: the origin clients reach the fake at when a proxy sits in front of it. It becomes the
  origin of the `browserUrl` that `POST /enroll/start` returns. Without it the fake uses the request's Host
  header over `http`, which is wrong behind an HTTPS proxy and is refused by the Hub's enrolment client as a
  different origin. The value is a scheme (`http` or `https`), a host and an optional port, with no path; the
  fake exits at start-up on anything else.
- `--host`, `--quiet`.

To demo the fake over Tailscale Serve:

```sh
node packages/banneret-relay-fake/src/bin.ts --port 4100 --public-origin https://<host>.<tailnet>.ts.net:8443
tailscale serve --https=8443 http://127.0.0.1:4100
```

In tests, `startFakeRelay({ port: 0 })` (also `publicOrigin`) from `@t3tools/banneret-relay-fake` returns the same server with
in-process helpers: `approve(confirmCode, person?)`, `refuse(confirmCode, reason)`, `seedNeeds`, `seedRepositories`,
`bumpCapabilities`, `publishBundle` and `removeStaff`.

The snapshot (README, "Snapshot") is built in memory. Files are stored once by the hash of their bytes, and each
person has a list of heads. The fake rebuilds every existing head whenever facts, needs, repositories or machines
change, and on every read of the head, so a head it serves is always current and it never answers 503. A read of
a file checks the caller's own retained heads (their last 16, plus any replaced less than 10 minutes ago), so
shared storage never grants access. `eventClock` replaces the clock that ages
the event log, so a test can prove the 24-hour `Last-Event-ID` bound and its `reset` event without waiting a
day.

## Run the conformance suite

```sh
cd packages/banneret-relay-fake
vp test run --config ../../vite.config.ts --dir .
```

Without settings it starts its own fake on an ephemeral port. To test another relay, such as the Go relay
in test mode, set its origin:

```sh
BANNERET_RELAY_URL=http://127.0.0.1:8080 vp test run --config ../../vite.config.ts --dir .
```

Use `POST /conformance/v1/pool/offer/expire` with `{sandboxId}` to expire an outstanding offer immediately.

For the shared machine cases, set the config key `pool` to the contents of `examples/pool-config.json`.
Host pairings always wait for founder confirmation, including on an auto-approving fake.

That relay must run with the network identity check off, and it must expose the control surface below.
Three tests run only against the fake, because they need a fresh store or a different configuration: the
empty-store start, the network identity check and the 24-hour event retention bound.

The Go test relay (banneret-platform) offers matching operator commands for the seeds (it also needs one for
`board/tracker`): `hub work seed`,
`hub lease age --task --hours`, `hub feed seed`, `hub graveyard seed --cause` and `hub checked seed --task --by
<login>` and `hub map seed --file -` (the plan on stdin). The control calls and the commands do the same thing. `board/seed` also accepts
`preview: {state, url?}` per task, which `GET /tasks/{taskId}` returns.

Today's Shipped block is `not_measured` (`work_tracker`, `not_configured`) until the first `board/seed`. After that
it lists one item per merged pull request on the board whose `mergedAt` is after the supplied `since` timestamp (all of them without a filter), newest first, at most 20, each with `pr {number, url, repo}`, the task's `ref` and `live`
`no_deploy`. A task with no board card always opened when the fake started and is open, because the fake reads no
issues.

A task seeded with tracker fields folds its comments, assignees and labels on every read with the shared fold
(`packages/contracts/src/leaseProtocol.ts`), using the enrolled founders as the people who may release someone else's
lease. Its `active` lease ages from the holder's latest comment or heartbeat; `conflict` and `incomplete` never age.
The card carries `lastRelease` from the fold, and `GET /tasks/{taskId}` the same. `feed/seed` with `type` `released`
gives each entry `reason` `done` and `freeToContinue` false.

The fake computes lease state from age on every read: by default, under 6 h `active`, from 6 h `stale`, from 24 h `expired`. A
held card with a stale or expired lease is in Stuck, never Free. A fact with a matching `taskId`, or a matching
`branch` (and `projectKey`, when the task has one), sets `lastSignalAt` to now and returns the lease to `active`.

`map/seed` takes a stage plan document (README, "Stage plan file") as the whole body, or `{plan, statuses?}` where
`statuses` maps an item id to a status for items with no `task` (the plan itself carries none). Seeding blockers this
way shows propagation: an item seeded `needs_you`, `sent_back` or `ruled_dead` blocks the items that rest on it, and
they block theirs in turn, each listing only its direct blockers in `blockedBy`. A seeded `blocked`, like a card that is
`blocked` on the board, counts as `planned` before the map applies its own `restsOn`, so the map never shows `blocked`
with an empty `blockedBy`. `hub map seed --file -`
reads the document from stdin and sends the same call. The fake accepts any `plan` and judges it the way a relay judges
its configured file, so a test can seed a broken one: a valid plan gives the map section and a `map` head file; an
invalid one (schema, duplicate or unknown ids, a `restsOn` that names nothing, a cycle) leaves the section present with a
`not_measured` map and the reason; `{plan: {"unreadable": true}}` does the same with `unreachable`; `{plan: null}` removes
the plan, so the section and the head key are omitted. The map joins an item's `task` to the seeded board cards by
`tracker`, `host`, `scope` and `key`. The fake's cards use tracker `github`, scope `example-org/example-app` and the key
`1`, `2`, ... in `board/seed` order. An item whose `task` matches no card still carries `task`: id `ref_<hash of the ref>`, the plan item's title (the fake reads no
issues), and the ref with a url; its status is `planned`, because the fake has no issue state. Changing whether the plan exists bumps the capabilities version.

## Lease fold fixtures

`fixtures/lease-fold/*.json` are the shared cases of the lease protocol fold: issue comments, assignees, labels,
founders and `now` in, the lease, `lastRelease` and the counted releases out. The format is in README, "Lease
protocol". `src/leaseFold.test.ts` runs every file through the Hub's fold, in the given order and reversed. The Go
relay runs the same files through its own fold; a new case goes in this folder first, and both must pass it.

```sh
cd packages/banneret-relay-fake
vp test run --config ../../vite.config.ts --dir . src/leaseFold.test.ts
```

## Changing the spec

This folder is the canonical contract. Change `openapi.yaml`, `README.md` and `examples/` here, update the fake
and the conformance suite in the same pull request, and run the suite. banneret-platform then copies the folder
into its mirror at `internal/hub/contract/relay-v1/`, where a drift test fails until the copy matches.

`scripts/banneret/sync-relay-spec.mjs` remains only for a one-off import from the platform, for example to take
over a change made there first:

```sh
node scripts/banneret/sync-relay-spec.mjs <banneret-platform>/internal/hub/contract/relay-v1 <commit-sha>
```

It overwrites the canonical `openapi.yaml`, `README.md` and `examples/` here with the platform's, so review the
diff before committing.

Pass `healthSources`, `dashboards`, `criticalRecipients` and `board` to `startFakeRelay`.
Each test source may supply a `measurement` with label, state, observedAt and optional summary.
A per-source `secret` enables signed incoming alarms. Sources and dashboards default to empty.
The fake stores alarms and replay receipts in SQLite. Its default `alarmDatabase` is `:memory:`;
supply a disposable database path to exercise restart behavior. Board clocks default to 21600
and 86400 seconds. See the [wire contract](README.md#optional-health-sources-dashboards-and-alarms).

To run both health configurations against another implementation, set `BANNERET_RELAY_URL`
to the manual-approval relay with the directory-only member `cy-example`. Set `BANNERET_RELAY_HEALTH_URL` to a second disposable relay
with auto-approved founder enrolment, webhook sources `alerts` and `cap_0` through `cap_5` using
`BANNERET_RELAY_HOOK_SECRET`,
30/90-second board clocks and a dashboard with id `metrics`, title `Metrics` and URL
`https://metrics.example.org`. Start the second relay with empty alarm state and rate windows.

Board seed PRs accept `baseBranch`, `approvals` (the wire object or null), `author` (login),
`canApprove` (eligible logins) and `approvalOnly` (GitHub's only blocker is review).
Omitting approvals seeds a measured branch with no approval rule. Personal reads resolve
eligible logins against active company people. Reseeding replaces the prior review state.

Pass `--chat` to enable the channel and thread calls. The fake keeps chat in memory and starts with a public `general` channel. Configure the real conformance target with `chat.enabled: true`.
