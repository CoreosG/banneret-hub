# Maintaining Banneret Hub

Banneret Hub is upstream T3 Code plus a thin layer of our own commits. Keep that layer thin: every line we change in an upstream file is a line that can conflict on the next sync.

## Rules for our changes

- **New behaviour goes in new files.** Upstream files get only the hook-in lines (a route registration, an import, one JSX element).
- **Fork screens are English-only:** plain strings, no `gt()`, no catalog keys. Their folders and files are excluded from the `no-untranslated-copy` rule by globs in `vite.config.ts` (`apps/web/src/banneret/**`, `components/ports/**`, the fork's file-transfer files and `state/banneret*.ts`). Put new fork screens under those folders, or add their path to that list.
- **Brand assets overwrite upstream's files in place** (`assets/{prod,nightly,dev}`, `apps/web/public`), generated by `node scripts/banneret/generate-icons.mjs`. The sync keeps ours automatically when both sides change them.
- **Installers are generated, not edited.** `scripts/banneret/make-install-scripts.mjs` derives `install.sh` / `install.ps1` from upstream's at release time, including what they print ("Installed Banneret Hub", "Run banneret"); `brand.test.ts` checks the output. If it fails after a sync, upstream changed the text it rewrites; adjust its rules.
- **Hooks are counted.** `node scripts/banneret/hook-budget.mjs` diffs `HEAD` against the upstream tag in `UPSTREAM_TAG` and counts the files and lines we changed in upstream files, leaving out the paths we overwrite or generate on purpose (brand assets, our own workflows, docs and scripts, lock files, `routeTree.gen.ts`). PRs and releases check both totals against `hook-budget.json`. Run with `--update` to accept reviewed growth within the hard line ceiling. Release notes show the measured change since the previous release.
- **The route tree is regenerated, not merged.** `node scripts/banneret/generate-route-tree.mjs` rewrites `apps/web/src/routeTree.gen.ts` with the TanStack router plugin's generator (needs `vp install --filter=@t3tools/web`). The sync runs it after every merge, so conflicts in that file resolve themselves.
- **Identity is guarded.** `node scripts/banneret/check-identity.mjs` fails when shipped source names official T3 Code identity (`~/.t3`, `com.t3tools.*`, `pingdotgg/t3code`, the `t3` launcher, `t3code://`, official hosts) beyond the reviewed baseline in `identity-baseline.json`. Bundled source is checked as shipped, after the build's rewrite (below), so it also fails when a rewrite rule stops matching or server copy still names the `t3` command. Rename the new hit, or review it and run with `--update`. `scripts/banneret/brand.test.ts` checks the rewrite rules, and `identity-bundle.test.ts` the built server.

- **Mobile-compatible.** CI runs the stock client from upstream v0.1.13 against the built Hub server. It pairs, opens a company project thread, sends a message and answers a provider request. Run `bash scripts/banneret/mobile/check.sh` when changing these paths. Update the pinned client only when changing the supported mobile release.

## Layout tests

A browser test whose assertions depend on layout runs across the viewport matrix: 900×700,
1920×1080, 2560×1080, 3440×1440 and 3840×2160 at scale 1, and 1920×1080 at scale 2 (a 4K screen at
200% OS scaling). A narrow window or an ultrawide one breaks layouts that look right at one desktop
size.

- Declare it with `forEachViewport` from `apps/web/src/banneret/test/viewports.ts`. That call is the
  layout tag: it names each case `[layout] … at <size>`. Every other browser test runs once, at its
  own size.
- Mount at the size the matrix set. A shared harness must not resize the window for a layout test.
- Use the helper's assertions for overlap, clipping, clickability, line length and centring.
- Each case calls `at.screenshot()` while its UI is up. Capture once per case: a large capture
  takes seconds on a loaded runner, and the case has the usual test timeout.
- Captures are off unless `VITE_LAYOUT_SHOTS` is set, and need `--no-file-parallelism`: a capture
  takes focus from test files running beside it, which fails their keyboard tests. From `apps/web`:
  `VITE_LAYOUT_SHOTS=1 vp test run --project browser --no-file-parallelism -t '\[layout\]' <files>`.
- Screenshots land in `.vitest-viewports/<test>/<size>.png` at the repository root. CI runs the
  matrix as its own step and uploads them as the `layout-screenshots` artifact.
- A PR that changes layout shows the per-size screenshots. Look at them: the assertions do not catch
  everything.

## Identity

|                               | Value                                                                                                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| App name                      | Banneret Hub                                                                                                                      |
| App id                        | `com.coreosg.banneret-hub`                                                                                                        |
| Home                          | `~/.banneret`, overridable with `BANNERET_HOME`                                                                                   |
| Command                       | `banneret` (the executable inside `~/.banneret/runtime/versions/<v>/` keeps upstream's `t3` name)                                 |
| Default port                  | 3793                                                                                                                              |
| Deep-link scheme              | `banneret://` (`banneret-dev://` in development), so official T3 Code never opens our links                                       |
| Background service            | systemd user unit `banneret-hub.service`, launchd `com.coreosg.banneret-hub.service`, Windows task `banneret-hub-<domain>-<user>` |
| T3 Connect, product analytics | off (no relay or Clerk keys at build time; analytics key and host blank)                                                          |
| Server process title          | `banneret` (set first thing in the server entry by `brand.mjs`; the executable file stays `t3`)                                   |
| Discovery paths               | upstream's `/.well-known/t3/environment` and `/.well-known/t3/desktop-readiness`, kept on purpose (below)                         |

The discovery paths stay upstream's. They are part of the wire protocol every T3 client and peer
speaks: the T3 mobile app (Banneret ships none, so phones use it), peer links, the desktop readiness
probe, `packages/tailscale` and T3 Connect's reachability check all read `/.well-known/t3/environment`. Renaming them gains nothing: a client
reaches a server only at an address it was given, and it checks the environment id in the answer,
so an official T3 server is never taken for ours. They name no state or link that official T3 Code
could pick up, unlike the home, scheme, service and variables above.

UI copy still says "T3 Code" in source. `scripts/banneret/brand.mjs` rewrites it to "Banneret Hub" in
production bundles only (web, server and desktop `vite.config.ts`), and re-keys the translation
catalogs to match, because General Translation keys each string by a hash of its English source. Tests
and dev servers keep upstream's text.

The same rewrite renames the environment variables that would point Banneret Hub at official T3
state (`ENV_RENAMES`: `T3CODE_HOME` becomes `BANNERET_HOME`, and likewise the install bin dir, CLI
shim path, agent thread id, LAN switch, installer knobs, and the service's own
`T3_BOOT_SERVICE_UNIT` and `T3_SERVICE_LAUNCHER_CONTEXT`). Official T3 sets these in its agent
shells, so a Banneret command run there would otherwise use T3's home and take T3's service for its
own. Every reader and writer is in a rewritten bundle, and `make-install-scripts.mjs` renames every
`T3CODE_*` in the installers.

It also renames the app-link scheme (`SCHEME_RULES`): `t3code://` becomes `banneret://` in pair
links, prompt links, the Codex sign-in handoff, provider auth return URLs, the desktop's registered
scheme and the server's CORS origins. Each rule is anchored on upstream's exact text. The scheme is
also registered outside bundles, by hand: electron-builder `protocols` in
`scripts/build-desktop-artifact.ts`, the dev launcher, and `apps/desktop/resources/installer.nsh`
(electron-builder registers schemes on macOS and Linux only). Dev web servers keep `t3code-dev://`.

On the stock phone app, scan the terminal pairing QR or paste the HTTP(S) pairing URL. The separate `banneret://pair` link opens Banneret desktop. Company membership and orchestrator designations are visible on the Hub. On mobile, open the same thread under its project.

Source and tests keep upstream's names. `scripts/banneret/identity-bundle.test.ts` builds the server
with the plugin and runs it to prove the shipped values, and `check-identity.mjs` scans bundled
source after the rewrite, so a rule that stops matching after a sync fails the check. The service
names (`banneret-hub.service`, `com.coreosg.banneret-hub.service`, `banneret-hub-<domain>-<user>`)
are plain source edits in `bootService.ts`, `serviceLauncher.ts` and `cli/update.ts`.

The server build also passes `cli: true`, which renames the command: `Command.make("t3")` (help,
usage and the `--version` banner), quoted commands such as `` `t3 up` ``, the `t3@<version>` status
line, prose such as "Another t3 at", and the launcher lookups on PATH and in the install bin dir. The runtime executable, the npm package (`npx t3@...`) and
the hidden `t3 checkpoint` commit messages keep `t3`. In web and desktop copy, which `cli` does
not touch, every bundle rewrites only "t3 command" and a bare `` `t3` `` (`COMMAND_COPY_RULES`), as on
the About screen; other web copy that names the command still says `t3`. If the build fails with "cannot reproduce translation key",
General Translation changed its hashing: update `hashCatalogSource` to match `hashSource` in the
`generaltranslation` package.

## Versions

Upstream `X.Y.Z` becomes `X.Y.(Z*100 + n)`: upstream `0.1.12` ships as `0.1.1200`, our own follow-up releases on that base are `0.1.1201`, `0.1.1202`. Versions always increase, so updaters see every release as newer. Release tags are `v<version>` because remote hosts download the server from `releases/download/v<version>`.

Upstream tags never enter our tag namespace: local clones fetch them into `refs/upstream-tags/` (`git config --add remote.upstream.fetch '+refs/tags/*:refs/upstream-tags/*'` and `git config remote.upstream.tagOpt --no-tags`). `scripts/banneret/UPSTREAM_TAG` records the upstream tag `main` is built on.

## Syncing

`banneret-sync.yml` runs daily. It merges the newest upstream stable tag into `main`; on a clean merge (or conflicts only in brand assets and the route tree) it releases, otherwise it opens a `sync/<tag>` PR. To sync by hand:

```sh
git fetch upstream
git merge refs/upstream-tags/vX.Y.Z
echo vX.Y.Z > scripts/banneret/UPSTREAM_TAG
node scripts/banneret/generate-route-tree.mjs
node scripts/banneret/check-identity.mjs
node scripts/banneret/hook-budget.mjs
vp run check:changed
git push origin main && gh workflow run banneret-release.yml
```

Upstream's own workflows stay disabled in this repository; the sync job disables any new one.
